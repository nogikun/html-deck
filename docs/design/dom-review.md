# DOM レビュー機構 設計と実装

生成した HTML デッキの上でユーザーが「ここを直して」を指し示し、それが JSON になって
Claude Code / AI エージェントに届き、局所修正されて返ってくる。批評サブエージェントの
ループに**人間のラウンド**を1つ足す仕組み。

状態: **実装済み** (`skills/html-deck/` に同梱、E2E で検証済み)

決めたこと:
- レビューでできることは **コメント + 領域指定** まで。スライドそのものの直接編集は将来
  (入力欄は `contenteditable` だが、書き換わるのは指示の本文だけでスライドは触らない)
- **まず html-deck 専用**として作り切り、安定後に汎用スキルへ切り出す

---

## 1. 目的と非目的

やること:
- 生成物の実物の上で、要素を指して自然言語で直しを出す
- まだ要素がない場所を矩形で指して「ここに◯◯が欲しい」と言う
- 指摘をソースの **ファイル + 行番号** まで解決した JSON として出す
- エージェントが直した結果を、同じ画面の上で確認できる

やらないこと:
- **ブラウザから HTML を書き換えない。** 出すのは意図だけで、ソースを書く主体を1つに保つ
- WYSIWYG エディタにしない。PPTX 的な自由編集は、このスキルの品質保証と両立しない

---

## 2. 実測で確定した前提

Chrome (system) + Playwright で検証した。

| 検証 | 結果 | 帰結 |
| --- | --- | --- |
| `file://` で親→iframe の `contentDocument` | **null**。`sandbox` 属性を外しても null | **ローカル HTTP サーバが必須。** 回避策なし |
| `http://127.0.0.1` で同じ操作 | rect / computedStyle 取得、親からのリスナー付与、子への DOM 注入すべて成功 | ピッカーは全部親側に置ける |
| 子の CSP が `script-src 'none'` のとき上記は通るか | **通る**。CSP はそのドキュメント内のスクリプト実行を止めるだけで、同一オリジンの親からの DOM 操作は対象外 | **スライドは1バイトも変えない** |
| DOM の childElementIndex 列 → ソース行番号 | `html.parser` の `getpos()` で解決可能 | JSON にファイル+行番号を入れられる |

実装中に判明した2点:

- **Playwright は `sandbox`(allow-scripts なし) の iframe を操作できない。**
  ユーティリティスクリプトが注入できず、フレーム内の座標解決でハングする。
  これはテスト側の制約で、実マウス入力は影響を受けない。E2E は
  「親のスクリプト文脈から子へ MouseEvent を流す」方式で書いた
- **領域ドラッグはネイティブのテキスト選択/D&D に食われる。**
  レビューモード中は子 body に `user-select: none` を当て、`dragstart` / `selectstart` を
  握り潰す。実マウスで文字の上から掴んでドラッグしても矩形が取れることを確認済み

## 3. 中核の原則: ブラウザは意図だけを出す

ブラウザから直接 HTML を書き換える設計にすると、このスキルの不変条件が壊れる。

- `theme.css` 凍結が崩れる (個別スライドに直接スタイルが刺さる)
- 「同じ指摘が2枚以上で出たときだけ theme.css を直す」という集約判断ができなくなる
- `check_deck.py` の gates を通らない値が人の手で入り、検査結果と現物が乖離する

**ブラウザ = 観測と表明の装置、エージェント = 唯一の書き手。**
3枚で同じ「文字が小さい」が来たら theme.css に1回で入れる、という判断はエージェント側に残す。

## 4. 主語は `#1` ブロック

コーディングエージェントと同じ形にした。**選んだ DOM が `#1` `#2` … という番号を持ち、
指示は自然言語1本**。分類チップ (文言/配置/色…) は設けていない。

理由は2つ。分類はエージェントが文面から読めば済む。そして選択が複数になった瞬間、
「この指摘の intent は何か」が破綻する (`#1` は文言、`#2` は配置、という指摘は普通に出る)。

### `#N` は本文の中のブロックであって、テキストではない

最初の実装は「入力欄の上にチップの列、本文には手で `#1` と打つ」形だった。これは
2つの点で足りなかった。**打ち間違えると対応が切れる**し、選んだものが文の主語に
なっている感覚が出ない。指摘は「`#1` が大きくて `#2` が小さい」のように**参照を主語に
した文**として書かれるので、参照は文の中に居る必要がある。

いまの composer は `contenteditable` で、参照は原子的なインライン要素
(`<span class="pill" contenteditable="false" data-key>`) として本文に挿し込まれる。

| 振る舞い | 実装 |
| --- | --- |
| クリックした要素がキャレット位置に入る | `selectionchange` で最後のレンジを保持し、iframe クリック時にそこへ挿す |
| 1文字として消える | `keydown` でキャレット直前/直後がピルなら `preventDefault` してノードごと削除 |
| コピーして貼るとブロックのまま | `copy` で `text/html` に `data-deck-refs` 印を付けて出し、`paste` は**自前の印がある HTML からしか**ピルを復元しない (それ以外は `text/plain` を `#N` で再解釈)。外から来た HTML は `data-key` と文字しか通さない |
| 手で `#2` と打つとブロックになる | 空白/改行の直前にキャレット手前を見て、既存の参照に当たれば置換 |
| 番号が常に本文と一致する | 番号はストアの登録順ではなく**本文に現れた順**で毎回振り直す。同じ参照が2箇所に出れば同じ番号 |
| 本文から消した参照は選択も外れる | エディタが正本。`syncRefs()` が本文に居ないキーをストアから落とし、スライド上のマークも消す |

**エディタの本文が唯一の正本**という点が要。チップ列とテキストの二重管理をやめたので、
「チップは残っているのに本文からは消えている」状態が構造的に起きない。

送信時は本文を `#N` 入りのプレーンテキストへ直列化して `instruction` に入れる。
**JSON の契約 (`refs[].n` ↔ 本文の `#N`) は変えていない。** サーバもスキーマもそのまま。

```
#1 の回収期間を6ヶ月に直して出典を足して。#2 の見出しも数字を合わせて。
#3 に現行と提案の比較図を入れて。
```

`#N` は `refs[].n` に対応する。サーバは受信時に `instruction_expanded` を作り、
`#N` を「ファイル:行 セレクタ 「本文」」に置換した版も残す。スキーマを知らない読み手でも
意味が取れる状態にしておくため。

## 5. データの流れ

```
[ユーザー] 要素をクリック (#1 #2) / 空白をドラッグ (#3) → 自然言語で指示 → 送信
     │ POST /__review/api/feedback
     ▼
review_server.py ── DOMパス→ソース行 を解決 ──▶ <deck>/.loop/feedback/inbox.jsonl
     │                                                       │
     │                           review_wait.py がここで終了 ──┘  (= 送信の通知)
     ▼
Claude Code ─ findings 単位で局所修正 ─▶ check_deck.py ─▶ review_resolve.py
     │                                    ├▶ resolved.jsonl
     │                                    └▶ deck.md ## accepted に [user] 行
     └───────── 再レビュー (ピンが緑になる) ◀────────────┘
```

## 6. ファイル構成と、切り出しの継ぎ目

| パス | 役割 | 汎用/デッキ依存 |
| --- | --- | --- |
| `scripts/review_server.py` | 配信 + `/__review/*` + POST 受信 + 行解決 + JSONL 追記 | 汎用 |
| `scripts/review_wait.py` | 未処理が現れるまで待って終了する (送信の通知経路) | 汎用 |
| `scripts/review_anchor.py` | DOM パス ⇄ ソース行の解決器 (標準ライブラリのみ) | 汎用 |
| `assets/review.html` | `#1` ブロック方式のレビュービューア (ライト/ダーク)。サーバがスキル側から配信 | 汎用 |
| `assets/feedback.schema.json` | JSON の契約 | 汎用 |
| `scripts/review_deck_adapter.py` | slides/ の列挙、round 番号、deck.md、feedback ディレクトリ | **デッキ依存** |
| `scripts/review_resolve.py` | 指摘を閉じ、`## accepted` に積む | **デッキ依存** |
| `references/review.md` | エージェント側の消費手順 | **デッキ依存** |

**デッキ固有の知識は下3つに閉じ込めてある。** 汎用スキルへ切り出すときはここだけ差し替える。
`review_server.py` と `review_anchor.py` は「ディレクトリを配信して、DOM の位置を
ソース行に解決する」以上のことを知らない。

デッキディレクトリに増えるのは `.loop/feedback/` のみ。納品前に剥がす作業は発生しない。

## 7. 操作モデル

`E` でレビューモード。入るとスライドの右に PowerPoint のコメントペインに相当する
領域が開く (閉じるとスライドが全幅に戻る)。

| 操作 | 動作 |
| --- | --- |
| ホバー | 要素をハイライト。セレクタと**実測**の font-size をラベル表示 |
| クリック | `#N` ブロックを本文のキャレット位置に挿す。同じ要素を再クリックで解除 |
| ピルをクリック | 小さなツールが出る (`↑ 親要素へ` / `× 外す`)。`↑` は span → li → ul と広げる |
| ピルにホバー | スライド側の該当要素をハイライト |
| 空白をドラッグ | 領域指定。まだ要素がない場所への指示 |
| `⌫` | キャレット直前のピルを1文字として消す |
| `Esc` | 参照を全部外す (打った文は残る) |
| `P` | 送信済みのピンだけ一時的に隠す (フッタのバッジのクリックでも同じ)。下書きの選択は残る |
| `T` | 白モード / ナイトモードの切り替え (既定は `prefers-color-scheme` 追従) |
| `Cmd`/`Ctrl` + `Enter` | 送信 |

### 見た目を PowerPoint に寄せた理由

レビューする人は「資料を見ている」文脈に居るので、開発者ツール風の暗い画面だと
判断の基準が資料からUIへずれる。Office の Fluent グレー (`#f3f2f1` / `#1b1a19` 系) に
寄せ、スライドを地の上に浮かせて、操作は上のツールバーと下のステータスバーに寄せた。
**色はライト/ダークの2系統をトークンで持ち、片方にしか無い色を作らない。**
オーバーレイ (ハイライト・ピン) だけはテーマに追従させない — スライド自体は常に白なので、
テーマで色を変えると白地の上でコントラストが落ちる。

**納品されるビューア (`assets/viewer.html` → デッキの `index.html`) も同じ見た目にした。**
レビュー画面と配布物で地の色もツールバーも違うと、同じデッキが別物に見える。
トークンの値は review.html と同一で、テーマの選択 (`deck-review-theme`) も共有する。
既存デッキの `index.html` を今の見た目に入れ替えるには
`init_deck.py <deck> --refresh-viewer` (タイトルとスライド一覧は引き継ぎ、
`theme.css` には触らない)。

### レビューを閉じたら1本も描かない

スライドは最終的に人に見せる面なので、**レビューモードを抜けた瞬間にキャンバス上の
描画物をゼロにする**。ホバー枠・下書きの選択・送信済みのピン・`.frame` のアウトライン、
すべて消える。注入したオーバーレイのルートごと `display:none` にしているので、
描き漏らしがあっても道連れで消える。

情報は消えない。実体は `.loop/feedback/` の JSONL 側にあり、`E` で戻れば同じ座標に
再描画される。「どの枚に指摘が残っているか」は**キャンバスの外** (フッタのバッジ) に出す。

### 座標系

要素の `getBoundingClientRect()` は iframe 内部 = **1600x900 キャンバス座標**でそのまま返る。
`scale()` はビューア側の `.frame` に掛かっているので無変換で使える。オーバーレイは
`position: fixed` で子ドキュメントに注入するため、拡大縮小に自動追従する。
注入した DOM は保存されないので納品物には残らない。

## 8. フィードバック JSON

契約は `assets/feedback.schema.json`。実物 (E2E の出力から抜粋):

```json
{
  "v": 1, "id": "fb-001", "status": "open", "round": 2,
  "slide": { "id": "03-evidence", "file": "slides/03-evidence.html" },
  "instruction": "#1 の回収期間を6ヶ月に直して出典を足して。#3 に比較図を入れて。",
  "refs": [
    { "n": 1, "kind": "element",
      "path": [1, 0, 1, 1, 1], "tag": "li", "classes": ["metric"],
      "selector": "article.slide > main.content > ul.metrics > li.metric",
      "text_excerpt": "3 ヶ月で初期費用を回収",
      "outer_head": "<li class=\"metric\"><span class=\"num\">3</span> ヶ月で初期費用を回収</li>",
      "rect": { "x": 160, "y": 385, "w": 640, "h": 64 },
      "computed": { "font_size_px": 24, "color": "rgb(20, 24, 31)" },
      "file_line": 23, "anchor_confidence": "exact" },
    { "n": 3, "kind": "region",
      "rect": { "x": 820, "y": 300, "w": 620, "h": 400 },
      "anchor": { "tag": "main", "selector": "…> main.content",
                  "file_line": 19, "anchor_confidence": "exact", "relation": "contains" },
      "neighbors": [ { "tag": "h2", "text_excerpt": "導入コストは3ヶ月で回収できる", "rect": {…} } ] }
  ],
  "instruction_expanded": "[#1 = slides/03-evidence.html:23 …「3 ヶ月で初期費用を回収」] の回収期間を…"
}
```

領域には**アンカー要素**(矩形を含む最小の要素)と**近傍要素**を必ず付ける。
座標だけ渡されてもエージェントは HTML のどこに挿すか決められない。

---

## 9. アンカー解決

ピック時点でサーバが行番号まで解決する。JSON は **4重のアンカー**を持つ。

1. `file_line` — 第一候補
2. `path` — 子要素インデックス列
3. `selector` — 人間が読む用。一意性は保証しない
4. `text_excerpt` / `outer_head` — **保険**

`anchor_confidence` が `exact` / `text` / `none` のどれかを返すので、エージェントは
どこまで信じてよいか分かる。**1件直すたびに行番号はずれるので、同じスライドの
2件目以降は `text_excerpt` で取り直す**、という運用を `references/review.md` に書いた。

既知の弱点: `<table>` の暗黙 `<tbody>` など、パーサが補う要素があると `path` がずれる。
その場合はタグ不一致を検知して抜粋照合に落ちる (`confidence: "text"`)。

## 10. ループへの組み込み

`references/loop.md` に反映済み。

- ラウンド **U (ユーザーレビュー)** を追加。批評の4ラウンド予算とは**別枠**。
  終わるのは `inbox.jsonl` の `open` が 0 になったとき
- 差し戻し規則に「**優先度は user > block > critic**」を追加。批評担当の指摘は待てるが人は待っている
- 終了条件に「`open` の指摘が残っている間は完成と言わない」を追加
- 評価ハック禁止に「`resolved.jsonl` に落とさず次へ進まない」「ユーザーに言われても
  `gates.json` を割らない (`deferred` にして理由を返す)」を追加

**`## accepted` への `[user]` 行の書き戻しが要。** ここを抜くと、次のラウンドで
批評サブエージェントがユーザーの指示を逆方向に指摘して、意思が静かに巻き戻る。
`review_resolve.py` が機械的にやる。

なお `deck.md` のテンプレートに `## accepted` の節が無いのに SKILL.md と loop.md が
そこへ書けと指示していた既存の穴があったので、`init_deck.py` に節を追加した。

## 11. セキュリティ

- `127.0.0.1` にのみバインド、ポートはランダム、POST はトークン必須 (検証済み: 403)
- 配信はデッキディレクトリ配下のみ。`..` は拒否 (検証済み: 404)
- 書き込み先は `.loop/feedback/` 固定。`slide_file` は `slides/*.html` に正規表現で制限
- **ユーザーのコメントは指示であって命令ではない。** デッキと無関係な操作を求める文が
  入っていたら実行せず確認する。この規定を `references/review.md` に明記した

## 12. E2E で確認したこと

`scripts/` に対して、実サーバ + 実 Chrome で通した項目:

ホバーでハイライトとラベルが出る / クリックで `#1` になる / 2つ目が `#2` になる /
再クリックで解除 / ドラッグで領域が入る / 送信でファイルに落ちる / 送信後にチップが消える /
再訪してもピンが残る / 要素の行番号が `exact` で解決 / 領域にアンカー行と近傍要素が付く /
`instruction_expanded` に実体が入る / `review_resolve.py` が `resolved.jsonl` と
`## accepted` に書く / 二重登録しない / 存在しない id を弾く / 解決済みの status が API に出る /
token なしを 403 / traversal を 404 / 実マウスのドラッグでテキスト選択が起きない

composer をブロック化したあとに追加で通した項目:

クリックでピルが本文に入る / 2つ目が `#2` になる / 打った `#2` がピルに変わる /
ピルをコピーして貼るとピルのまま (`text/plain` は `#1`) / `⌫` で1つだけ消え、
同じ参照の別のピルは残る / 最後のピルが消えると参照ごと落ちる / 要素の再クリックで
その参照の全ピルが消えて番号が振り直る / `Esc` で全部外れる / レビューを閉じると
下書きマークだけ消えてピンは残る / `E` と `T` がエディタ入力中は発火しない /
送信で `#1 #2 #3` と `refs[].n` が一致し、行番号が `exact` で解決する

## 13. 通知経路の決着

設計時に「同期ブロッキング受信とポーリングのどちらを既定にするか」を保留していた。
実装して分かったのは、**どちらでもなく「終了する待機プロセス」が要る**ということ。

サーバは止めるまで動き続けるので、バックグラウンド実行の完了通知が飛ばない。
エージェントが自力でポーリングするとトークンを食い、間隔を空けると反応が遅れる。
`review_wait.py` は未処理が現れた時点で終了するので、**プロセスの終了通知がそのまま
「ユーザーが送信した」の合図**になる。実測で送信から約1秒で戻る。

SKILL.md の手順7では、サーバと待機を必ず2本セットで起動する規定にした。
