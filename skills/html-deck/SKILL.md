# HTML Deck

材料を渡されたら、**ゴールを1つ決めて、そこに届くまで直し続ける**。
1回の生成で完成させようとしない。初期案は下書きで、価値は差し戻しループの側にある。

このスキルが引き受ける範囲は、企画・デザイン・実装・検査・修正の全部。
ユーザーに求めるのは**最初のインタビュー1回と、最後の承認1回だけ**。
途中で細かく確認を取ると、ユーザーが評価器の代わりをさせられることになる。

---

## 全体の流れ

```
材料を読む → インタビュー(1回・4問) → 情報量の予算を決める → 骨格生成 → デザイン → 全枚実装
                                                                          ↓
                      ユーザーへ提示 ← 終了判定 ← 批評(Sonnet) ← 決定的検査 ←┘
                            ↓             └──────── 局所修正 ────────────┘
                    レビューモードで指摘 (#1 #2 … + 自然言語)
                            ↓
                      局所修正 → 再検査 → resolved に記録 → ## accepted に積む
                            └────────── ユーザーが納得するまで ──────────┘
```

## 入口が途中のとき

このスキルは0から作る前提で書いてあるが、途中から呼ばれることが多い。
**手順1から律儀に始めない。** 該当する手順へ直接飛ぶ。

| 言われたこと | 行き先 |
| --- | --- |
| 「スライド作って」「この資料をスライドに」 | 手順0から (**インタビューを飛ばさない**) |
| 「デッキ見せて」「レビューさせて」「直したいところがある」 | **手順7**。サーバと待機を起動して URL を渡す |
| 「指摘読んで」「送ったやつ直して」 | **手順8**。未読のスレッドを処理する |
| 「3枚目のここを直して」(チャットで口頭) | 手順8の修正部分だけ。指摘 JSON は要らない |
| 「文字が小さい」「はみ出してる」 | 手順5の検査から |

デッキの場所を言われていないときは、`deck.md` と `slides/` の両方があるディレクトリを探す。
1つなら黙ってそれを使う。複数あるときだけ聞く。

## 0. 材料を読む

### まず、使えるスキルを拾う

**材料を開く前に、この環境で利用できるスキルの一覧に目を通す。** 一覧は環境ごとに
変わるので、ここに挙げたものが必ずあるとは限らないし、挙げていない有用なものが
増えていることもある。見るのは**この1回だけ**。作り始めてから探し直さない。

| いつ | スキル | 何に使うか |
| --- | --- | --- |
| **手順3・必須** | `frontend-design` | デザインの方向を決める前に必ず読む。読まずに theme.css を書かない |
| 手順0 | `pptx` `docx` `xlsx` `pdf` | **インポート専用。** 材料がその形式で渡されたとき、中身を読むためだけに使う |
| 手順4・8 | `natural-japanese` | claim と本文の日本語。言い切りが鈍い・訳文調になったとき |

拾うのは `frontend-design` と、材料・依頼から要ると分かるものだけ。
`frontend-design` が無い環境なら、その旨を1行伝えてから
`references/quality-contract.md` の数値だけで進める (黙って飛ばさない)。

**書き出しには使わない。** `pptx` `docx` `xlsx` `pdf` は材料を読む口であって、
出口ではない。納品物は HTML と、`scripts/export_pdf.py` が出す固定PDF。

### 材料を読む

渡されたファイル・URL・会話の内容を全部読む。この時点で次を自分の中で確定させる:
誰に向けた資料か / 見終わった人に何をしてほしいか / 一番言いたい1文は何か。
材料に書いていなければ、材料から一番もっともらしい答えを立てる。ここで
ユーザーに丸投げして質問を並べない。**答えを持って聞きに行く。**

もう1つ、この段で拾っておく。**材料の中の「図にできる関係」**
(比較・順序・包含・数量の差) を書き出す。次のインタビューの選択肢も、
そのあとのストーリーボードの `visual` 列も、ここが空だと埋まらない。

## 1. 目指す状態をインタビューする（唯一の必須確認）

**ここが一番効く。** 資料の出来は作り方より「何のために作るか」で決まる。
`AskUserQuestion` を**1回**呼び、そこに**4問まとめて**入れる。1問ずつ何度も聞くのは
中断が増えるだけで、インタビューが濃くなるわけではない。

聞くのはこの4つ。順番も変えない。

| # | 聞くこと | なぜ要るか |
| --- | --- | --- |
| 1 | **見終わった人がどういう状態になっていてほしいか** | 以降の全ての合否条件になる |
| 2 | **どう見せる資料か** — 話しながら / 置いて読ませる / 両方 | 1枚の情報量の予算が変わる。聞かずに作ると必ず外す |
| 3 | **相手は誰で、何を決められる人か** | 前提の説明をどこから始めるかが決まる |
| 4 | **枚数と持ち時間** | 削る判断の根拠になる |

**選択肢は材料から作った具体文にする。** 一般語を並べた質問は、答えても何も決まらない。

- × 「情報を伝える」「理解を深める」「検討したい」
- ○ 「HTML-first を限定パイロットとして承認する判断ができる」
  「7つの配信プロトコルから自分の用途に合うものを選べる」

呼ぶのは**最大2回**。2回目を呼ぶのは、材料が薄くて**骨格が2通り以上に割れるとき**だけ
(例: 事例中心で行くか、仕組みの説明で行くかで枚の並びが変わる)。それ以外は答えを持って進む。
確認を重ねると、ユーザーが評価器の代わりをさせられる。

### 場面から情報量の予算を決める

質問2の答えをそのまま数値にする。決めたら**ラウンド0で1度だけ** `gates.json` に反映し、
理由を `deck.md` の `constraints` に書く (途中で変えるのは評価ハック)。

| 場面 | 1枚の日本語 | 考え方 |
| --- | --- | --- |
| 話しながら見せる | **300字** | 画面は話の裏付け。読ませると話が聞かれない |
| 置いて読ませる (配布・非同期) | 420〜520字 | 本文が主。ただし1枚1メッセージは崩さない |
| 両方 | 300字 + 話す内容は `deck.md` 側へ | 画面に全部載せない |

### そもそもこの資料が要るか

材料を読んだ結果、**1つの判断を伝えるだけで済む**ことがある。そのときはスライドを
作る前にそう言う。3行で足りる用件に15枚作るのは丁寧ではなく無駄。
**「作らない」も答えとして出してよい。** ただし1往復で決め、ユーザーが作ると言えば作る。

合意した内容は `deck.md` の `goal` / `situation` / `audience` / `constraints` に
そのまま書く。以降は確認を挟まない。ストーリーボードを作ったら**短く見せてから、
止められない限り着工する** (承認を待たない)。ユーザーの手を止めないことが、
このスキルのインターフェースの要件。

## 2. 骨格を作る

```bash
python <このスキルのディレクトリ>/scripts/init_deck.py <出力先> --title "デッキ名"
```

出力先の既定は、材料と同じディレクトリの `<slug>-deck/`。
`deck.md` / `theme.css` / `index.html`(ビューア) / `slides/` ができる。
`deck.md` の goal / situation / audience / takeaway / storyboard を埋める。
storyboard は1行1枚で、`claim`(言い切りの見出し) と `job`(比較/因果/構造/数量/例示/宣言) と
`visual`(その枚を何の絵で見せるか) と `問い(入)→問い(出)` を必ず書く。
**claim が名詞句になっている行は、まだ主張になっていない。**

### storyboard の段階で情報量を割る

実装に入る前に、表を**縦に読んで**次を確かめる。ここで直すのは1行の書き換えで済むが、
実装後だと1枚まるごと作り直しになる。

- `visual` 列が「なし」の行が**3つ以上続いていないか。** 続いているならどれかを図にする
  (`check_deck.py` が `text_only_streak` として落とす)。デッキ全体で図のある枚が**4割以上**
- `visual` が「箇条書き」の行が並んでいないか。箇条書きは形ではない。job が比較なら
  比較の絵、因果なら順序の絵になる (`references/layout-playbook.md`)
- 1行に claim が2つ入っていないか。**1枚1メッセージ。** 入っていたら2枚に割る
- 手順1で決めた1枚の字数を、`evidence` の量に掛けて総量を見る。総量が持ち時間を
  超えるなら、枚を増やすのではなく**節を落とす**

## 3. デザインを決めて theme.css に固定する

**`frontend-design` スキルを読む。ここは飛ばさない** (手順0 で拾ってあるはず)。
読んだうえで、このデッキ固有の方向を決める。
決めるのは4つだけ: **配色4〜6色 / 表示・本文・等幅の3書体 / 文字サイズ段階 / 記憶に残る装置1つ**。
決めたら `theme.css` の TOKENS に書き、`deck.md` の `## design` にも残す。

制約が2つある。守らないと後段で全部やり直しになる。

- **外部フォントは読み込めない** (CSP・オフライン配布)。ローカルにある face か、
  `deck/fonts/` に置いた woff2 の相対参照のみ。スタック末尾に `system-ui` を必ず置く
- **1600x900 は固定なので px で書き切る**。`clamp()` も `cqh` も不要。
  実測値と指定値が一致するほど、この後の検査が効く

theme.css を決めたら以降は凍結する。触るのは「2枚以上で同じ指摘が出たとき」だけ
(理由は `references/loop.md`)。

## 4. 全枚を実装する

雛形は `assets/slide-template.html`。各スライドは独立したHTMLで、
`theme.css` を読み、自分の `<style>` にそのスライド固有のレイアウトだけを書く。
**`:root` のトークンを再定義しない。** 1枚の都合で全枚の色が変わる。

レイアウトは job から決める。型を当てはめない。手がかりは `references/layout-playbook.md`。
数値の初期値と根拠は `references/quality-contract.md`。迷ったら本文24px・見出し54px・
外周80px・1枚420字 (手順1で場面が「話しながら」なら300字) までから始める。

**文字で埋めない。** 箇条書きは6項目まで、1項目60字まで。60字を超えたら、それは
箇条書きの形をした段落で読まれない。関係 (比較/順序/包含/数量) が書かれているなら、
文ではなく図にする — それが storyboard の `visual` 列に書いてあるはず。

**図や画像を入れるなら `references/figures.md` を先に読む。** 方式の選び方
(手書きインラインSVG / draw.io / ラスタ)、配置パターン、図の中の数値契約がそこにある。
要点だけ先に: 図は必ず**インライン**で置く (`<img src="*.svg">` にすると中身を測れず、
図に対してだけ検査が無力になる)。図の中の文字は viewBox で縮むので、
指定値ではなく**実効サイズ**が20pxを割らないようにする。
draw.io を使う場合、上流スキルを `vendor/draw-io/` にそのまま同梱してある。

枚数が多いときは、実装を並列のサブエージェントに割ってよい。その場合も
`theme.css` と `deck.md` は共有の読み取り専用として渡し、書き換えさせない。

## 5. 決定的検査（批評より先）

```bash
uv run <このスキルのディレクトリ>/scripts/check_deck.py <deck-dir>
```

1600x900 のヘッドレスChromeで全枚を実測し、はみ出し・文字切れ・文字サイズ・
コントラスト・パレット逸脱・外部参照・情報密度・階層比を出す。
枚ごとの検査に加えて**並びの検査**も出る (`figure_coverage` / `text_only_streak` /
`deck_too_dense`)。これは1枚ずつ見ても分からない欠陥で、**どの1枚も合格のまま
デッキ全体が文字の壁になる**のを止めるためにある。1枚ずつ直すのではなく、
どの枚を図に置き換えるか・どこを統合するかで応える。
スクリーンショットとコンタクトシートを `.loop/round-N/` に保存し、
`index.html` のスライド一覧を同期したうえで、**ビューア越しに開いても共有CSSが
効いているか**まで確かめる (1枚ずつなら正しく、ビューアだと全スタイルが消える、
という事故が実際にあった)。

**`block` が1件でも残っている間は、批評サブエージェントを起動しない。**
機械が確実に見つけられる欠陥を自分で潰してから批評に出す。そうしないと
批評の指摘枠が体裁の修正で埋まり、「主張が伝わるか」に枠が回らない。

## 6. 批評を受けて差し戻す（Sonnetのサブエージェント）

block が 0 になったら、`Agent` ツールで批評担当を起動する。
**必ず `model: "sonnet"` を指定する。** 実装しているのはこのセッション自身なので、
同じモデルに採点させると自分の癖ごと見落とす。系列を分けることが目的。

サブエージェントの推論の深さはツール側から指定できないので、**プロンプトの冒頭で
「よく考えてから」と明示して思考量を上げる**。これは指定の代用であって同義ではない。

枚ごとの批評（未 pass の枚だけ、並列で起動してよい）:

```
subagent_type: "general-purpose",  model: "sonnet",  run_in_background: false
prompt:
  よく考えてから採点してほしい。まず <このスキルのディレクトリ>/agents/slide-critic.md を読み、
  そこの指示に完全に従うこと。
  - screenshot: <deck>/.loop/round-N/shots/03-evidence.png   ← 必ず Read で画像を見る
  - slide_contract: <deck.md の該当行をそのまま貼る>
  - deck_goal: <合意したゴール>
  - metrics: <report.json の該当スライドの metrics>
  - accepted: <deck.md の ## accepted をそのまま貼る>
  - user_intents: <review_thread.py <deck> brief --slide 03-evidence の出力を貼る>
  - html_path: <deck>/slides/03-evidence.html
  返答は指定のJSONのみ。
```

デッキ全体の批評（毎ラウンド1回）:

```
subagent_type: "general-purpose",  model: "sonnet",  run_in_background: false
prompt:
  よく考えてから判断してほしい。まず <このスキルのディレクトリ>/agents/deck-critic.md を読み、
  そこの指示に完全に従うこと。
  - contact_sheet: <deck>/.loop/round-N/contact-sheet.png   ← 必ず Read で画像を見る
  - storyboard / deck_goal / takeaway / audience / accepted: <deck.md から貼る>
  - user_intents: <review_thread.py <deck> brief の出力を貼る>
  返答は指定のJSONのみ。
```

返答は `.loop/round-N/critique.json` に**加工せず**保存する。要約して保存すると、
次のラウンドで何を直したのか追えなくなる。

**`user_intents` を渡し忘れない。** ユーザーがレビューで確定させた意図は
`deck.md` の `## accepted` にも1行で入っているが、批評担当には**なぜそう決めたか**まで
渡したほうが効く。`review_thread.py brief` がその形で出す。

**返答の `user_conflict` が空でなかったら、実装で直さない。** そこはユーザーが実物を見て
決めたことなので、批評担当の言い分をそのままユーザーに伝えて判断を仰ぐ
(「03の出典の置き方について、批評担当はこう見ている。どうするか」)。
黙って批評側に寄せると、ユーザーの意思が静かに巻き戻る。

修正は **findings 単位の局所修正だけ**。ついでに他を整えない。
修正前に現状を `.loop/best/` へコピーし、再検査で悪化した枚は戻す。
確定した判断は `deck.md` の `## accepted` に1行ずつ足す。これを次のラウンドの
批評担当に渡さないと、同じ場所を逆方向に指摘され続けて往復する。

## 7. 終了してユーザーへ返す

終了条件・停滞判定・予算・評価ハックの禁止事項は `references/loop.md` にまとめてある。
**批評担当を起動する前に一度読む。** 要点だけ:

- 全軸4以上 + `deck-critic` が pass → 完成
- 改善が2ラウンド連続で小さい → **自動で続けない。** 現物と残件を出して判断を仰ぐ
- 4ラウンドで打ち切り

返すときは、成果物の場所・ゴールに対する到達度・**直せなかった点**を明記する。
点数だけ並べない。**返す前に自分で `index.html` を開いて目で見る** — 検査が通ったことは
開いて確認しない理由にならない。

**渡す形は3つある。用途で選ぶ。**

| 形 | 出し方 | 何のため |
| --- | --- | --- |
| デッキ一式 | そのまま | 手直しを続ける。レビューもここから |
| **1枚のHTML** | `scripts/bundle_deck.py <deck>` | **人に送る。** 外部参照ゼロの1ファイルで、そのまま添付できる |
| 固定PDF | `uv run scripts/export_pdf.py <deck>` | 見た目を完全に固定する。印刷する |

`export_pdf.py` は、`theme.css` で指定した書体が**実際に描画に使われたか**を検査して、
代替書体に落ちていたら書き出さない。生成した環境に書体が無ければ「見た目を固定して
渡した」とは言えないため。承知のうえなら `--allow-font-fallback` を付ける。

どちらもレビュー画面の **PDF / 1枚HTML ボタン**から押せる (サーバ稼働中のみ)。

渡し方は、`Bash` を `run_in_background: true` で**2本**起動して URL を渡す。

```bash
python3 <このスキルのディレクトリ>/scripts/review_server.py <deck-dir> --open
```

```bash
python3 <このスキルのディレクトリ>/scripts/review_wait.py <deck-dir> --timeout 1800
```

**2本目を忘れない。** サーバは止めるまで動き続けるので完了通知が飛ばず、
1本目だけだと**ユーザーが指摘を送ったことに気づけない**。待機は指摘が届いた時点で
終了するので、その終了通知が「ユーザーが送信した」の合図になる。

URL を渡したら、`E` で要素をクリックすると入力欄に `#1` のブロックが入ること、
それを主語に書けることを1〜2行で伝える。使い方の全文をチャットに貼らない。
ユーザーは右ペインの凡例を見れば分かる。

**ビューアは1本しかない。** `index.html` とレビュー画面は同じファイルで、
`file://` で開くとレビュー機能が自分で畳まれる (親から iframe の中に到達できないため)。
見た目も操作も同じ。デッキを作った時期が古いと `index.html` だけ昔のままなので、
そのときは入れ替える。

```bash
python3 <このスキルのディレクトリ>/scripts/init_deck.py <deck-dir> --refresh-viewer
```

タイトルとスライド一覧は引き継ぐ。`theme.css` と `slides/` には触らない
(`--force` は theme.css ごと初期化してしまうので、既存デッキに使わない)。

`E` で閉じればスライドの上の枠とピンは1本も残らないので、**そのまま人に見せられる**。
指摘が残っているかはフッタのバッジ (`● 3`) で分かる。レビュー中に素の見た目を確かめたい
ときは `P` かそのバッジでピンだけ落とせる。

ブラウザを閉じたあとも見たいだけなら `index.html` を直接開けばよい
(レビュー機能とボタンは自動で消える。`file://` では要素を選べず、書き出しを走らせる
プロセスも無いため)。人に送るなら `bundle_deck.py` の1枚を渡す。

## 8. ユーザーの指摘を受けて直す

待機 (`review_wait.py`) が終了したら、その標準出力に未読のユーザー発言がそのまま入っている。
スレッドを読み直す必要はない。

**指摘1件 = 1本のスレッド = 1つの PR。** 会話して、検査結果を見て、**ユーザーがマージ**して
初めて確定する。エージェントは「直した (`proposed`)」までしか進められない。

```
待機が終了 (= ユーザーが発言) → スレッドごとにサブエージェント (deck-fixer)
      ↑                              │  context を渡す / 他のスレッドは渡さない
      │                              ▼
      │                        直す → review_check.py --level brief → post --state proposed
      │                              │
      │                        ユーザーが読む → 差し戻し または マージ
      └──────── 待機を張り直す。ユーザーが終わりと言うまで ────────────┘
```

**メインとサブの分担を崩さない。**

- サブ (`agents/deck-fixer.md`) は **`slides/NN.html` だけ**書く。1スレッドだけ見る
- **`theme.css` を書けるのはメインだけ。** サブは `review_thread.py escalate` で上げてくる。
  同じ `key` が別スライドで2件以上たまったら `decide` で一度に直し、関係スレッド全部に書き戻す
- メインが受け取るのはマージの結果だけ。**スレッドの会話をメインに持ち込まない**

**処理が終わったら待機を張り直す。** 張らないと次の指摘に気づけず、ユーザーは
送ったのに反応がない状態で待つことになる。ただし待機がタイムアウトで戻ってきたときは
**黙って張り直さない。** 一度「まだ見ていますか」と声をかける。無言で待ち続けると、
ユーザーからはセッションが固まったように見える。

**受け取り方・直し方・閉じ方は `references/review.md` に全部ある。着手前に読む。** 要点:

- **優先度は user > block > critic。** ユーザーが待っているのに批評の指摘を先に潰さない
- 位置は `file_line` を第一候補にするが、`anchor_confidence` を必ず見る。
  1件直すたびに行番号はずれるので、2件目以降は `text_excerpt` で取り直す
- **直したら必ず検査して、結果を添えて返す** (`review_check.py --thread <id> --level brief`)。
  `block > 0` のままではユーザーがマージできない (サーバが 409 で止める)
- ユーザーの指示でも `gates.json` は割らない。溢れるなら `deferred` にして理由と代案を返す
- **マージはユーザーが押す。** そのとき `deck.md` の `## accepted` に確定した意図が積まれる。
  積まれないと次のラウンドで批評担当が逆方向に指摘し、**ユーザーの意思が静かに巻き戻る**

返すときは、マージされた件数だけでなく**確認待ち (`proposed`) のまま残っているもの**と
**却下・保留したものとその理由**を必ず言う。`proposed` が残っている間は完成と言わない。

編集可能な `.pptx` は約束しない。HTML → PPTX の忠実な変換は検証していない。
PPTX が必須なら最初から `pptx` スキルで作る。

## このスキルが避けようとしている失敗

作る前に頭に入れておく。全部、1枚ずつ自由に作らせると必ず起きる。

- 各スライドが凝った見た目を競い、デッキの声が割れる → theme.css 凍結 + `palette_drift` 検査
- 1枚ずつは美しいが、全体の話が進まない → `deck-critic` が cut/merge/reorder を判断
- 見た目を優先して出典や数字が雑になる → 出典は主張と1対1、未出典の数値は禁止
- はみ出しを `overflow:hidden` で隠す → `clipped_text` として block
- 批評が往復して収束しない → `accepted` に確定判断を積む
- 点を上げること自体が目的になる → しきい値はラウンド0で固定、途中変更は結果を無効
- ユーザーが直させた箇所を、次のラウンドで批評担当が元に戻す → マージが
  `## accepted` に `[user]` 行を積み、以降の批評担当に必ず渡す
- ユーザーが指摘を送ったのに気づかず放置する → 手順7で `review_wait.py` を必ず一緒に張り、
  1周ごとに張り直す
