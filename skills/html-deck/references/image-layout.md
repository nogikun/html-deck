# 画像内の文字と操作箇所を、大きく見せる

操作画面・文字のある図、または「画像が小さい」と指摘された枚で使う。
写真など、文字や細部を読ませない画像に一律のJSONやOCRを要求しない。

## 1. 読ませたい対象を決め、JSONに残す

`assets/image-layout.example.json` をデッキの `image-layout.json` にコピーし、例の値を置き換える。
実資料の記録にするときは `example_only` を外す。必要ラベルの未測定分は `unmeasured_labels` に残す。
これはエージェントが使う制作記録で、現在のCLIが自動読込・自動最適化する設定ではない。
全画像の索引は作らず、配置の判断が必要な画像だけを記録する。

- `source_size_px`: 元画像の実画素数。表示寸法と混同しない。
- `focus_box_px`: 元画像の左上基準 `[x, y, 幅, 高さ]`。画像の範囲内に収め、必要なラベル・部品を切らない。
- `focus_source` / `must_read`: 領域をどう決め、何を読ませるか。アイコンなら部品名も書く。
- `measurement`: OCR・元ページのDOM・人手確認など、実際に使った方法と測定値。未測定は `null`。
  OCRの字形の箱の高さはCSSの文字サイズではない。認識信頼度が返らない環境では捏造しない。
- `placement` / `verification`: 推定した配置と、描画後の確認結果を分ける。

OCRは、既に使える環境があれば利用する。専用モデル・サーバー・WindowsのOCR・画像解析ライブラリを
スキルの必須依存にしない。文字サイズが測れない場合は数値予測を保留し、画像を見て配置して確認する。

## 2. 占有率ではなく、必要な表示サイズから決める

まず対象の文字・部品の大きさを測る。小さな注記やコメントなど、読ませない文字を混ぜない。
複数の字形を測れた場合は、最小値のノイズを避けるため下位10%点などを目安にできる。
必要ラベルがOCRで欠けている場合、そのラベルの大きさを測れたとは扱わない。
残りの字形から計算できても、その予測は測定できた字形に限る。未測定の対象を含む合格判定には使わない。

比例拡大で、元の注目領域の幅を `Cw`、必要な字形の高さを `g`、閲覧時の縮小倍率を `v`、
閲覧時に確保したい字形高を `t` とすると:

```text
必要なスライド上の表示幅 = Cw × t / (g × v)
表示高さ = 注目領域の高さ × 表示幅 / Cw
占有率 = 表示幅 × 表示高さ / (1600 × 900)
```

`g`・`v`・`t` は正の値が必要。不明・0の値で計算しない。
閲覧倍率は実際のビューアや予定する表示環境から求める。目標の字形高は案件の仮定として記録する。
例の **63%・16pxは検証用の仮値で、推奨標準や全案件の既定値ではない**。

次の順で構図を選ぶ:

1. 全体を見せても必要な文字・部品が判別できるなら、全体表示。
2. 余分な領域が多いなら、必要部分の拡大。場所が分かりにくい場合だけ、位置確認用の全体図を添える。
3. 見出し・説明・出典と一緒に収まらないなら、説明する操作や領域を分けてスライドを分割する。

全体画面を一律に半分の幅へ押し込まない。画面占有率は結果として記録し、万能な最適比率を仮定しない。
情報を大きくするために必要な軸・凡例・ボタン・対象の種類まで落とさない。

## 3. 部分拡大を実装する

拡大図には、元画像のどこを示したかを短いキャプションで添える。
全体図を添える場合は「位置の確認用」と区別し、そこに細かい文字を読ませない。
説明するボタンやラベルが、拡大範囲の中に実在することを確認する。

切り出した画像を `figure > img` で配置するか、対応する環境ではCSSの `object-view-box` で表示範囲を決める。
後者は元画像を変更しないが、[ブラウザによって対応が異なる](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/object-view-box)。
使用する場合は実際のブラウザで対応と描画を確認し、未対応環境へ配るなら切り出し画像などに置き換える。
PPTX出力も同じ範囲を再現するとは限らないため、対応を約束する前に出力結果を見る。

```html
<figure>
  <img data-image-id="filter" src="../assets/images/filter.png"
       alt="検索フィルタのタイプ・時間・アップロード日"
       style="width:1003.3px;height:495.3px;object-fit:contain;
              object-view-box:inset(145px 463px 354px 190px)">
  <figcaption>検索フィルタ上部の3列を拡大。</figcaption>
</figure>
```

この例は元画像1048×694、注目領域 `[190,145,395,195]`。HTMLの `data-image-id` をJSONの `id` と対応させる。
実際の領域・寸法は、画像ごとに計算して置き換える。

**拡大しても元の細部は増えない。** 注目領域の幅を表示幅で割った値も確認し、
1未満なら元画素より拡大していることを記録する。ぼけや低コントラストが残る場合は、再撮影・分割・文章の補足を選ぶ。
この実効比が1未満であること自体は、意図した部分拡大のレビュー項目。必要な文字・部品の判別と
元画像のぼけを確認して採否を記録する。`references/figures.md` のCLIの解像度blockはファイル全体の幅を
基準にするため、この実効比とは区別する。実際に出たblockを、この記録だけで解除してよいという意味ではない。
画像の解像度検査はファイル全体の幅を基準にするため、CSSで部分表示した後の実効解像度を十分には評価できない。
部分表示を使って解像度の指摘を隠したり、画像を単に再サンプリングして合格にしない。

## 4. 実際の表示で確かめる

`html-deck-check` の後、予定する閲覧倍率で確認する。
必要な文字が読めるか、操作部品が判別できるか、説明と画像の対象が一致するかを見る。
OCRで必要ラベルを再検出する場合も、完全一致数を人の正読率にしない。
誤認や欠落は目視確認へ回し、アイコンの検査には文字OCRを使わない。
確認者がエージェントなら、人間による検証済みとは記録しない。

`verification` を更新し、批評担当に該当画像のJSONと最終スクリーンショットを渡す。
単一HTMLでの表示とページ送り、納品する場合はPDF・PPTXも確認する。

色数・エントロピー・輪郭密度・認識文字数・文字領域率は補助値として追加できるが、
測定方法・正規化サイズ・量子化などの条件も残す。異なる方法の値を直接比較しない。
色の多い写真を文字の多いUIより大きくすべきだと決めたり、未校正の重みで可読性の点数を作らない。

## 確認ケース

| ケース | 確認する判断 |
| --- | --- |
| メニューの文字が小さい | 必要ラベルと領域を指定し、全体表示と部分拡大を比べる |
| 元画像やOCRに必要なラベルがない | 存在・サイズを推測せず、別画像か目視確認へ回す |
| 字形高が未測定、OCRがない | 数値予測を保留し、視覚確認した配置を残す |
| アイコンで操作する | 部品の形と位置を目視確認。OCR不一致を失敗扱いにしない |
| 部分拡大でも説明と一緒に入らない | 必要情報を削る前に分割する |
