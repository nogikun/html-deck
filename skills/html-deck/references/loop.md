# ループ制御

このデッキは1回で完成しない前提で作る。初期生成は下書きであり、
到達品質は「何回で、どこまで直せたか」で決まる。ここはその回し方の規定。

## 1ラウンドの形

```
build / patch  →  html-deck-check (決定的)  →  critics (Sonnet)  →  triage  →  次のラウンド
                        ↑                                              │
                        └──────── block が残る間はここで折り返す ────────┘
```

**決定的検査が先、批評は後。** これは順番の趣味ではなくコストの問題。
はみ出し・小さすぎる文字・低コントラストは機械が確実に見つけられる。
それらが残ったまま批評に出すと、批評担当の指摘枠がその修正で埋まり、
本来見てほしい「主張が伝わるか」に枠が回らない。

`html-deck-check` の block が1件でもある間は、批評担当を起動しない。自分で直して再検査する。

### 並びの検査は1枚ずつ直さない

`figure_coverage` / `text_only_streak` / `deck_too_dense` は**枚の並び**に対する所見で、
1枚ずつの修正では消えない。無理に消そうとすると、意味のない図を各枚に足す方向へ動く
(これは評価ハックにあたる)。応え方は3つだけ。

1. その区間の**どれか1枚を図に置き換える** (箇条書きに書かれていた関係を絵にする)
2. **2枚を1枚に統合する** — 同じ主張を分けて書いているだけなら1枚で足りる
3. 場面と合っているなら `deck.md` の `accepted` に理由を書いて残す
   (例: 「配布用の仕様書なので 05〜08 は表が本体。図に置き換えない」)

**1と2は storyboard の `visual` 列に戻って決める。** 実装側だけで足した図は、
主張と繋がらないので次のラウンドで批評担当に落とされる。

`html-deck-check` はスライド単体だけでなく、**実際の配布経路 (index.html のビューア) も開いて確かめる。**
1枚ずつ開けば正しく見えるのに、ビューア越しだと共有CSSが丸ごと効かない、という事故が
実際に起きた (`sandbox` が不透明オリジンを作り、スライド側CSPの `'self'` が一致しなくなる)。
素のHTMLが表示されるだけでコンソールにも何も出ないので、**納品前に必ず一度は自分で
index.html を開いて目で見る。** 検査を通ったことは、開いて確認しない理由にならない。

## 各ラウンドでやること

| ラウンド | 内容 | 批評担当 |
| --- | --- | --- |
| 0 | **インタビュー**・契約合意・デザイン・ストーリーボード確定。しきい値をここで固定する | なし |
| 1 | 全枚実装 → 決定的検査 → block を潰す | slide-critic 全枚 + deck-critic |
| 2 | 指摘の局所修正 → 再検査 | 前回 pass 以外の枚 + deck-critic |
| 3 | 同上 | 前回 pass 以外の枚のみ |
| 4 | 予算上限。残件を持ってユーザーへ | なし |
| U | **ユーザーレビュー。** 人間が回すので批評の4ラウンド予算とは別枠 | なし (人間) |

ラウンド U は `html-deck-review` でデッキを渡したあと、ユーザーが指摘を出すたびに回る。
批評ラウンドと違って回数の上限は置かない。**指摘1件 = 1本のスレッド = 1つの PR** で、
終わるのは全スレッドが `merged` / `closed` / `rejected` になったとき。
**`proposed` (確認待ち) が残っている間は終わっていない** — 直したかどうかではなく、
ユーザーが見て認めたかどうかで決まる。

ラウンド U の中では**1スレッド = 1サブエージェント** (`agents/deck-fixer.md`)。
スレッドをまたいで文脈を運ばない。共有トークン (`theme.css`) を動かす判断だけは
メインに残り、サブは `html-deck-thread escalate` で上げてくる。手順は `references/review.md`。

批評担当は **Sonnet** で起動する。実装しているのはこのセッション(Opus)なので、
同じモデルに採点させると自分の癖を見落とす。系列を分けることが目的で、
「安いから」ではない。

## 差し戻しの適用ルール

1. **findings 単位で適用する。** 指摘が3件なら3箇所だけ直す。
   ついでに他も整えたくなるが、それをやると何が効いたか分からなくなり、
   悪化したときに戻せない。
2. **修正前に `.loop/best/` へ現状をコピーする。** 修正後の検査で
   block が増えた、または軸のスコアが下がった枚は、`.loop/best/` から戻す。
   1枚の点を上げるために別の軸を犠牲にした版を残さないための仕掛け。
3. **theme.css を直すのは、2枚以上で同じ指摘が出たときだけ。**
   1枚の都合で共有トークンを触ると、他の枚が静かに壊れる。触ったら全枚を再検査する。
4. **`accepted` に記録する。** 「この密度で行く」「この見出しはこの長さで確定」など、
   判断が固まったものを deck.md の `## accepted` に1行ずつ足す。次のラウンドの
   批評担当にこれを渡す。渡さないと、同じ場所を逆方向に指摘し続けて往復する。
5. **ユーザー由来の指摘は他より先に処理し、直したら検査を添えて `proposed` で返す。**
   優先度は user > block > critic。批評担当の指摘は待てるが、人は待っている。
   確定させるのは**ユーザーのマージ**で、そのとき `## accepted` に `[user]` 行が積まれ、
   以降の批評担当がそれを覆さなくなる。ここを飛ばすと、ユーザーが直させた箇所が
   次のラウンドで静かに元へ戻る。

## 終了条件

先に来たものを採用する。

| 条件 | 動作 |
| --- | --- |
| block 0 かつ 全枚 全軸 4以上 かつ deck-critic が `pass` | 完成。ユーザーへ提示して承認を取る |
| block 0 だが軸が届かない状態で、改善が2ラウンド連続で小さい | 停滞。**自動で続けない。** 残件と現物をユーザーへ出して判断を仰ぐ |
| 4ラウンド到達 | 打ち切り。残件を明示して提示する |
| 未確定 (`open` / `proposed`) のスレッドが残っている | **完成と言わない。** 人間が出した宿題が未処理のまま |
| `figure_coverage` が残っている | 各枚に図を足して消さない。構成で応え、応えられないなら `accepted` に理由を残す |
| 批評担当同士の結論が食い違う (slide-critic は pass、deck-critic が cut を要求) | 判断材料を並べてユーザーへ返す |
| 修正で block が増え、戻しても再発する | 局所修正では届かない。構成から作り直すか、その枚を落とす |

「改善が小さい」の判定に固定点数のしきい値を置かない。批評担当の採点には
±1程度の揺れがあるので、**軸スコアの合計が前回から動かず、かつ high severity の
findings が減っていない**ことをもって停滞と見なす。

## 予算

1デッキあたりの目安: 批評担当の起動は合計20回まで、決定的検査は無制限
(ローカルで数秒・無料なので、実装のたびに回してよい)。
批評の起動が20回に近づいたら、残りをユーザーに報告してから続ける。

## 評価をハックしない

このループは、点を上げること自体が目的になった瞬間に無意味になる。
特に次はやらない。

- しきい値を途中で緩める (`gates.json` を書き換えて block を消す)。
  場面に応じた `max_ja_chars` の設定は**ラウンド0まで**。以降は動かさない
- 意味のない飾りの図やアイコンを各枚に足して `figure_coverage` を通す
  (検査は画面の4%未満を図と数えないが、4%を超える無意味な図は通ってしまう。
  ここは自分で律する)
- 検査に映らない場所へ文字を逃がす (画像化、`overflow:hidden` で切る、`opacity:.05`)
- 批評担当に「pass にして」と書いた文脈を渡す
- 批評担当に `user_intents` を渡さない (ユーザーの決定が次のラウンドで静かに巻き戻る)
- 批評担当の `user_conflict` を、ユーザーに伝えずに実装で直す
- `theme.css` を触ったのに、マージ済みのスレッドへ `notify` しない
  (ユーザーが確認して合意した絵と、納品される絵が食い違う)
- 指摘のない枚まで作り直して、スコアの見かけを揃える
- ユーザーの指摘を `proposed` のまま「直しました」と報告して次へ進む
  (合意していないものを終わったことにする。マージするのはユーザーで、エージェントではない)
- 検査を回さずに `proposed` にする / `block` が残っているのに直したと言う
- サブエージェントが自分の判断で `theme.css` を書く
  (1枚のために共有トークンを動かすと、他の枚が静かに壊れる。集約の判断はメインの仕事)
- ユーザーに言われたからといって `gates.json` を割る。溢れるなら `deferred` にして理由を返す

しきい値を変える正当な場面はある (印刷専用、超大型スクリーン、英語のみ等)。
その場合は**ラウンド0で1度だけ**変更し、理由を deck.md の `constraints` に書く。
ラウンドの途中で変えたものは、結果を無効として扱う。

## 記録

各ラウンドで `.loop/round-N/` に残るもの:

- `report.json` — 決定的検査の全数値と所見
- `shots/*.png` — 1600x900 のスクリーンショット
- `contact-sheet.png` — 全枚の一覧
- `critique.json` — 批評担当の返答をそのまま (加工しない)

ラウンドをまたいで `.loop/feedback/` に残るもの:

- `threads/fb-NNN.jsonl` — 指摘1件ごとの会話ログ (追記専用)。**起票も状態もここが正本**
- `escalations.jsonl` — サブ→メインのテーマ判断依頼の台帳
- `merged.jsonl` — マージで確定した意図。次のレビューと批評担当に渡す

`.loop/history.md` に1ラウンド1行で書き足す:
`round N | block X → Y | 平均軸 A → B | 適用した修正の数 | 停止理由(あれば)`

これは自己満足の記録ではなく、停滞判定とユーザーへの説明の根拠になる。
