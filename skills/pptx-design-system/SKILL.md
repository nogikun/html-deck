# PPTX Design System

**毎回ゼロから決めないために、決め終わったことだけを 1 ファイルに置く。**

このスキルが作るのは資料そのものではなく、資料を作るときに参照する標準である。
成果物は 1 つの `.pptx` で、2 つの層を同居させる。

| 層 | 中身 | 効き方 |
|---|---|---|
| 機能として効く層 | テーマ配色 12 スロット / テーマフォント / スライドマスターの枠 | ユーザーが新しく挿した図形・表・グラフが最初から正しい色と書体で出る |
| 判断として効く層 | 規約スライド 16 枚 | 「赤をいつ使うか」「何 pt まで小さくしてよいか」など、測れない判断を言葉で固定する |

片方だけだと必ず失敗する。テーマだけでは使い方が伝わらず、文書だけではファイルに反映されない。

## このスキルを使わない場合

- スライドの**中身**を作りたい → `html-deck` (HTML デッキ) か `pptx` (編集可能な .pptx)
- ロゴやブランドマークそのものを作りたい → このスキルの範囲外
- Word / Excel のテンプレート → `docx` / `xlsx`

## 入口が途中のとき

| 言われたこと | 行き先 |
|---|---|
| 「標準スタイルを作って」「テンプレートがほしい」 | 手順 1 から |
| 既存 .pptx を渡されて「ルールを分析して」 | **手順 2 だけ**。テンプレート化は聞かれてから |
| 「色だけ変えて」「別案件用に差し替えて」 | **手順 4**。`scripts/tokens.py` の accent1 を変えて再生成 |
| 「配布したい」「.potx にして」 | **手順 6** |

## 手順 1 — 必須 4 項目を聞く

**聞くのはこれだけ。**全部答えさせようとすると着手が遅れる。4 つ取ったら一度作って見せる。

1. **主役の色 1 色** — 画面の 2〜3 割を占める色。HEX でも「ロゴのこの青」でもよい
2. **使える和文書体** — 配布先にない書体を指定すると全員の画面で崩れる
3. **キャンバス比** — 16:9 / 16:10 / 4:3
4. **資料名とフッターに出す所属**

主役の色がまだないなら、こちらから提案する。実績のある決め方は 3 つ。

- 題材のブランド色をそのまま使う
- 使うイラスト素材の既定色に合わせる (unDraw なら `#6C63FF`)。挿絵と資料が同じ色で喋る
- ロゴから最も面積の大きい色を取る

**既存の .pptx があるなら、聞く前に手順 2 で測る。** 聞くより速くて正確。

残りの項目 (ロゴ・欧文書体・帯の色・意味色・投影環境・配布先) は既定値がある。
一覧と既定の根拠は `references/build-spec.md` 4.2 節。

## 手順 2 — 既存資料があるなら測る

.pptx は XML の zip なので、好みを聞くより実測が速い。
手順と、何が読み取れるかは `references/build-spec.md` 4.4 節に 9 ステップで書いてある。要点だけ:

- `ppt/theme/theme1.xml` の `clrScheme` が Office 既定のままなら、
  **デザインは毎回スライド上で手作業されていて保存先がない状態**。テンプレート化の効果が最大になる。
- `schemeClr val` の頻度で accent1 が突出していれば、その人は既に「主役 1 色」で作っている。
- `sz` の最頻値が本文サイズ、タイトルプレースホルダの `a:off` / `a:ext` がマージンと帯の高さ。
- 複数資料に共通して出る書体が、その人の記名性。

**数値だけで終わらせない。** PowerPoint でレンダリングして実画像を通しで見る (手順 5 のコマンド)。
構図の型と、積み上げ・グレーアウトのような手癖は画像でしか拾えない。

分析結果の書き方の実例が `references/design-theory.md`。
既存資料 4 本 157 枚を測って理論に落とした全文で、そのまま雛形として使える。

## 手順 3 — 既定の理論を確認する

座標・文字サイズ階層・構図の型は `references/design-theory.md` の実測に基づく既定値があり、
**相手の好みを聞いて変えるものではない**。変える必要が出たら、まず理論のほうを疑う。

| 項目 | 既定 (16:9 / 13.333 × 7.5 in) |
|---|---|
| 左右マージン | 0.92 in |
| タイトル帯 | 全幅・高さ 1.00 in。セクション名を入れる。1 枚ごとの要約は入れない |
| アクセント罫 | y = 1.04 in / 3pt。accent1 を全ページに 1 本だけ通す |
| 本文領域 | y 1.35 → 6.70 in |
| フッター帯 | y 6.94 in / 高さ 0.56。左: 資料名 / 中央: 所属 / 右: ページ |
| 文字サイズ | 54 / 44 / 40 / 36 / 24 / 20 / 16 / 12pt の 8 段。12pt 未満は使わない |
| 文章量 | 1 枚 100 字が中央値、250 字で 2 枚に割る |
| 色の配分 | 無彩色 7 割 / accent1 2.5 割 / その他 0.5 割 |
| 意味色 | 赤=否定 緑=肯定 橙=注目 青=参照 灰=中立。装飾で色を選ばない |
| 形の語彙 | rect / roundRect / line / ellipse / triangle の 5 つ。影・グラデーションは使わない |
| 面と線 | **線で分けず、面で分ける。**箱を細い罫で囲まない。地より一段沈めた面 (`lt2`) を置く。罫を残すのはグラフの軸と、白に近い色見本の輪郭だけ |

16:10 で使うときは文字サイズを全段 ×0.83 すれば階層がそのまま移る。

## 手順 4 — 生成する

`scripts/tokens.py` の `TOKENS` を書き換えて実行する。**色・書体・名前だけを変える。**

```bash
uv run --with python-pptx python scripts/make_design_pptx.py
```

`assets/design.pptx` が出る。既存の `assets/design.pptx` は参照実装なので、
別案件用に作るときは出力先を変えるか、生成後にコピーして渡す。

実装上の落とし穴は `references/build-spec.md` 6 節にまとめてある。特に効くのは 2 つ。

- **テーマは python-pptx では書けない。** 保存後に zip を開いて
  `<a:clrScheme>` / `<a:fontScheme>` を丸ごと差し替える。ここを直さないと
  「見本は合っているのに、ユーザーが新しく挿した図形は既定色で出る」状態になる。
  `xml.etree.ElementTree` で再書き出しすると名前空間接頭辞が壊れるので使わない。
- **マスターへの図形追加にも API がない。** `master.shapes._spTree` に `<p:sp>` を append する。
  塗りは `srgbClr` ではなく `schemeClr` で参照すると、accent1 を差し替えたとき罫も追従する。

## 手順 5 — 検査する

**LibreOffice は使わない。**和文書体の代替で字幅が変わるため、はみ出し判定が当てにならない。
PowerPoint がある環境なら PowerPoint に描かせるのが唯一信用できる。

```powershell
$pp = New-Object -ComObject PowerPoint.Application
$pres = $pp.Presentations.Open("<絶対パス>\design.pptx", $true, $false, $false)
$pres.Export("<出力先>", "PNG", 1600, 900)
$pres.SlideMaster.Theme.ThemeColorScheme.Colors(5).RGB
$pres.SlideMaster.CustomLayouts | ForEach-Object { $_.Name }
$pres.Close(); $pp.Quit()
```

`Colors(5).RGB` は BGR 並びの整数。`#6C63FF` なら `16737132` (= 0xFF636C)。

書き出した PNG は 12 枚ずつのコンタクトシートにして**通しで見る**。
1 枚ずつ見てもマージンのばらつきと帯の高さの揺れは見つからない。

チェック項目は `references/build-spec.md` 7 節。最低限これだけは見る。

- [ ] 本文領域から文字や図形がはみ出していない
- [ ] 文字がフッター帯に重なっていない
- [ ] カードやピルから文字が溢れていない
- [ ] 白に近い色見本に枠線が付いている (枠がないと見えない)
- [ ] 帯・罫・フッターの位置が全枚で同一
- [ ] テーマ配色・テーマフォントが PowerPoint 側から読めている
- [ ] プレースホルダ文字が残っていない

最初のレンダリングはたいてい 2〜3 箇所はみ出す。直して、直した枚だけ再描画して、そこで止める。

## 手順 6 — 配る

PowerPoint でデザインを保存する形式は 3 つあり、役割が違う。混同すると配布事故になる。

| 形式 | 中身 | 使いどころ |
|---|---|---|
| `.thmx` | 配色・フォント・効果のみ | 色と書体だけを他の資料に移す |
| `.potx` | テーマ + マスター + レイアウト + 背景図 | 新規作成の出発点として配る |
| `.pptx` | 上記 + 規約スライド | 指針そのものとして保持・閲覧する |

このスキルが作るのは `.pptx`。配布時はそこから［名前を付けて保存］で `.potx` を派生させ、
元の `.pptx` は指針の正本として残す。

第三者書体 (Google Fonts 等。既定の Noto Sans JP もこれ) を使った場合は、配布先で入れてもらうか、
［ファイル］▸［オプション］▸［保存］▸［ファイルにフォントを埋め込む］を有効にして配る。

| `references/design-theory.md` | 既存資料 4 本 157 枚の実測から取り出したデザイン理論。分析の書き方の雛形でもある |

| `scripts/kit.py` | 描画プリミティブ (面・ピル・カード・帯) |

## 守ること

- **変えてよいのは accent1 と、表紙・フッターの文字列だけ。**
  帯の高さ、罫の位置、文字サイズ階層を資料ごとに変えた時点で、そのファイルは標準の外に出る。
  変えたくなったら標準のほうを直して、次からの全部に効かせる。
- **規約は禁止形で書く。** 「やらないこと」のほうが守られる。
- **最小構成は 9 枚**(表紙 / 役割 / 原則 / パレット / 配分と意味 / 書体 / 文字サイズ / 骨格 / やらないこと / 運用)。
  時間がないときはここだけでも指針として機能する。残り 7 枚は方向が確認できてから足す。
