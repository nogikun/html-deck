# 標準スタイル design.pptx の作成仕様

ステータス: 初版 (`assets/design.pptx` として実装済み)
作成日: 2026-11-03
関連: `references/design-theory.md` (既存資料の分析結果)、`scripts/` (生成器)

## 1. 目的

「会社やチームが 1 つ持っておく、色・書体・文字サイズ・余白の指針としての PowerPoint ファイル」を
作るための手順と、**作る前に聞いておくべき情報**を定義する。

この仕様は 2 つの読まれ方をする。

1. 既にある `design.pptx` を直すとき、どこを触ればよいかの地図として。
2. 別の人・別のプロジェクト向けに新しく作るとき、何を聞けば着手できるかの一覧として。

## 2. 非目的

- デザインの良し悪しを自動採点すること。
- PowerPoint のデザインアイデア (Designer) を再実装すること。
- ロゴやブランドマークそのものを作ること。本仕様は既にあるものを配置する側に限る。
- スライド 1 枚ごとの作図を自動化すること。テンプレートは枠と規約までを担い、中身は人が作る。

## 3. 成果物の定義

PowerPoint で「デザインを保存する」には 3 つの形式があり、役割が違う。混同すると配布事故になる。

| 形式 | 中身 | 使いどころ |
|---|---|---|
| `.thmx` (テーマ) | 配色・フォント・効果のみ。レイアウトも背景図も持たない | 色と書体だけを他の資料に移したいとき |
| `.potx` (テンプレート) | テーマ + スライドマスター + レイアウト + 背景図 | 新規作成の出発点として配るとき |
| `.pptx` (本仕様の成果物) | 上記すべて + **規約を人が読める形で載せたスライド** | 指針そのものとして保持・閲覧するとき |

本仕様が作るのは 3 番目である。**機能として効く部分 (テーマ・マスター) と、
判断として効く部分 (規約スライド) を 1 ファイルに同居させる**のが狙いで、
これにより「色は揃うが使い方が伝わらない」「文書はあるがファイルに反映されていない」の両方を避ける。

配布時は、この `.pptx` から［名前を付けて保存］で `.potx` を派生させる。
元の `.pptx` は指針の正本として残す。

## 4. 受け入れ情報 (intake)

ユーザーから「自分用に作ってほしい」と言われたとき、以下を順に確認する。
**必須は 4 項目だけ**で、残りは既定値か既存資料からの推定で埋められる。
全部答えさせようとすると着手が遅れるので、必須を取ったら一度作って見せる。

### 4.1 必須 (これがないと着手できない)

| # | 聞くこと | 例 | なぜ必要か |
|---|---|---|---|
| 1 | **主役の色 1 色** (accent1) | `#6C63FF` / 「ロゴのこの青」/「Obsidian の紫」 | 画面の 2〜3 割を占める。ここが決まらないと何も決まらない |
| 2 | **使える和文書体** | 「Noto Sans JP」/「Mac と Windows の両方で」/「社給 PC にあるものだけ」 | 配布先にない書体を指定すると全員の画面で崩れる |
| 3 | **キャンバス比** | 16:9 / 16:10 / 4:3 | 全座標と文字サイズ階層がここに紐づく |
| 4 | **資料名とフッターに出す所属** | 「Presentation Design System / nogikun」 | 表紙とフッターの文字列。空のまま配ると必ず残る |

主役の色がまだない場合は、次のいずれかで決める。これは分析で実際に使われていた決め方である。

- 題材のブランド色をそのまま使う (Obsidian の資料 → Obsidian の紫)。
- 使うイラスト素材の既定色に合わせる (unDraw なら `#6C63FF`)。挿絵と資料が同じ色で喋る。
- ロゴから最も面積の大きい色を取る。

### 4.2 あると精度が上がる (なければ既定値)

| 聞くこと | 既定値 | 既定の根拠 |
|---|---|---|
| ロゴ画像 (SVG か透過 PNG) | なし | 表紙とフッターに置く。なければ文字だけで成立する設計 |
| 欧文書体 | Arial | 等幅が必要なら Consolas。和文書体の欧文グリフは避ける |
| 見出し書体を分けるか | 同じ家族をウェイトで分ける (Noto Sans JP Medium / 標準)。ボールドは掛けない | 配布先で入れる書体が1つで済む。Mac・Windows・Linux で同じ字形になる |
| タイトル帯の色 | `#3F3D56` | 無彩色寄りの暗色。有彩色の帯は主役の色と競合する |
| 意味色 (肯定 / 否定 / 注目 / 参照 / 中立) | 緑 `#098544` / 赤 `#C00000` / 橙 `#FF9800` / 青 `#0070C0` / 灰 `#747474` | 既存資料 4 本で一貫していた対応 |
| 想定する投影環境 | 会議室プロジェクタ | 大画面・手元配布なら最小文字を 12pt → 10pt まで許容できる |
| 既存資料があるか | — | **あれば最優先。4.4 の手順で実測し、既定値より優先する** |
| 配布先 (社内のみ / 社外 / 公開) | 社内 | 社外・公開なら素材のライセンス表記欄を規約スライドに足す |

### 4.3 聞かないこと

次は聞いても答えが揺れるだけなので、こちらで決めて提示し、違ったら直す。

- 文字サイズの各段の pt 値 — 比率で決まるので、基準 1 つ (本文) が決まれば残りは導出できる。
- 余白の数値 — キャンバス比から比率で決まる。
- レイアウトの種類 — 構図の型 6 つで足りる。足りないと分かってから足す。
- 角丸の半径、罫線の太さ — 2 種類に固定するのが規約の本体であって、値そのものは重要でない。

### 4.4 既存資料がある場合の推定手順

ユーザーが過去に作った .pptx があるなら、聞くより測ったほうが速く正確である。
`references/design-theory.md` はこの手順で作った。

1. `ppt/slides/slideN.xml` 全件から `srgbClr val` の頻度を数える → 実際に使っている色。
2. `schemeClr val` の頻度を数える → テーマスロットのうち実際に効いているもの。
   accent1 が突出していれば、その人は既に「主役 1 色」で作っている。
3. `ppt/theme/theme1.xml` の `clrScheme` を見る → Office 既定のままなら、
   **デザインはスライド上の手作業で、保存先がない状態**。テンプレート化の効果が最も大きい。
4. `sz` 属性の頻度 → 文字サイズ階層。最頻値が本文、タイトル帯の中の値がタイトル。
5. `latin` / `ea` の `typeface` 頻度 → 書体。複数資料に共通して出る書体がその人の記名性。
6. タイトルプレースホルダの `a:off` / `a:ext` → マージンと帯の高さ。
   同じ座標が複数枚で繰り返されていれば、それが骨格。
7. `prstGeom prst` の頻度 → 形の語彙。
8. `<a:t>` の総文字数を枚ごとに出して中央値と 90 パーセンタイル → 文章量の基準。
9. PowerPoint でレンダリングして実画像を見る (7 節参照)。数値では出ない構図の型と
   積み上げ・グレーアウトの手癖はここでしか拾えない。

## 5. 中身の構成

規約スライドは 16 枚。順番にも意味がある (何が決まっているか → どう使うか)。

| # | 枚 | 必須 | 載せるもの |
|---|---|---|---|
| 1 | 表紙 | ○ | 資料名。表紙レイアウトの見本を兼ねる |
| 2 | この資料の役割 | ○ | 機能として効く部分と判断として効く部分の区別 |
| 3 | 設計の原則 | ○ | 5 行。これだけ読めば大筋が分かる粒度 |
| 4 | カラーパレット | ○ | 12 スロットすべてに HEX・スロット名・役割 |
| 5 | 色の配分と意味 | ○ | 配分比、意味色の対応、エンティティへの色の固定 |
| 6 | 書体 | ○ | 見出し / 本文の 2 系統、実際のサンプル文、埋め込みの手順 |
| 7 | 文字サイズ | ○ | 全段の pt 値 + 実寸見本 + 用途 |
| 8 | 画面の骨格 | ○ | 帯・罫・本文領域・フッターの座標図 |
| 9 | レイアウトの型 | — | 構図 6 種のサムネイルと使いどころ |
| 10 | 図解の部品 | — | ピル / カード / 送り / 吹き出しの実物 |
| 11 | 強調の作法 | — | 色で差す・他を落とす・積み上げる |
| 12 | 表とグラフ | — | 見出し行の塗り、自分の行の強調、系列 1 色主義 |
| 13 | イラストと画像 | — | 画風の統一、面積比、キャプション |
| 14 | やらないこと | ○ | 8 項目。規約は禁止形のほうが守られる |
| 15 | 運用 | ○ | 差し替え手順、.potx / .thmx、フォント埋め込み |
| 16 | 裏表紙 | — | 閉じの 1 行 |

「○」は最小構成。時間がないときはこの 9 枚だけでも指針として機能する。

## 6. 実装上の要点

生成は `scripts/` 以下の 4 モジュール (python-pptx + 後処理)。
`tokens.py` (決める値) → `kit.py` (描画部品) → `slides.py` (16 枚の中身) → `make_design_pptx.py` (入口) の一方向で依存する。詰まりやすい点だけ記す。

### 6.1 テーマは python-pptx では書けない — zip を開いて差し替える

python-pptx はスライド上の図形は書けるが、`ppt/theme/theme1.xml` の `clrScheme` /
`fontScheme` を編集する API を持たない。しかし **PowerPoint の［配色］［フォント］に出るのはここだけ**で、
ここを直さないと「見本は合っているのに、ユーザーが新しく挿した図形は既定色で出る」状態になる。

保存後に zip を開き、正規表現で `<a:clrScheme>…</a:clrScheme>` と
`<a:fontScheme>…</a:fontScheme>` を丸ごと差し替える。
`xml.etree.ElementTree` で再書き出しすると名前空間接頭辞が書き換わって壊れるので使わない。

スロットの並び順は固定で、`dk1 / lt1 / dk2 / lt2 / accent1-6 / hlink / folHlink`。
マスターの `clrMap` が `bg1→lt1, tx1→dk1, bg2→lt2, tx2→dk2` を担うので、
スライド側では `bg1` `tx1` などの名前で参照する。

和文を扱うので `<a:font script="Jpan" typeface="…"/>` を major / minor 両方に入れる。
`<a:ea>` だけだと環境によって拾われない。

### 6.2 マスターへの図形追加も API がない

`MasterShapes` に `add_shape` はない。`master.shapes._spTree` に
`<p:sp>` を組み立てて `append` する。塗りは `srgbClr` ではなく `schemeClr` で参照すると、
後から accent1 を差し替えたときに罫の色も追従する。

マスターのプレースホルダは全部消す。帯・罫・フッター帯だけを置いた状態が、
「新規スライドが最初から標準の見た目になる」最小構成である。

### 6.3 不要レイアウトは消す

既定テンプレートは 11 レイアウトを持つが、実際に使うのは 5 つ程度。
残すものは日本語名に改名し、残りは `SlideLayouts.remove()` で落とす。
指針ファイルにレイアウトが 11 個並んでいると、どれが標準か分からなくなる。

### 6.4 テキストボックスの内部余白

python-pptx の既定テキストボックスには内部余白がある。
図形や罫と文字の左端を揃えるときは `margin_left = margin_right = 0` を必ず設定する。
揃っていないズレは 1 枚ごとには気づけず、通しで見たときに全部ずれて見える。

## 7. 検査

LibreOffice のレンダリングは和文書体の代替で字幅が変わるため、はみ出し判定に使えない。
**PowerPoint がある環境なら PowerPoint で描かせる**のが唯一信用できる方法。

```powershell
$pp = New-Object -ComObject PowerPoint.Application
$pres = $pp.Presentations.Open("<絶対パス>\design.pptx", $true, $false, $false)
$pres.Export("<出力先>", "PNG", 1600, 900)
$pres.SlideMaster.Theme.ThemeColorScheme.Colors(5).RGB   # accent1 が入ったかの確認 (BGR 整数)
$pres.SlideMaster.CustomLayouts | ForEach-Object { $_.Name }
$pres.Close(); $pp.Quit()
```

`Colors(5).RGB` は BGR 並びの整数を返す。`#6C63FF` なら `16737132` (= 0xFF636C)。

書き出した PNG は 12 枚ずつのコンタクトシートにまとめて一覧で見る。
通しで見ないと、マージンのばらつきと帯の高さの揺れは見つからない。

### 検査項目

- [ ] 本文領域 (左右マージンの内側) から文字や図形がはみ出していない
- [ ] 文字がフッター帯に重なっていない
- [ ] カードやピルから文字が溢れていない
- [ ] 白に近い色見本に枠線が付いている (枠がないと見えない)
- [ ] 帯・罫・フッターの位置が全枚で同一
- [ ] テーマ配色・テーマフォントが PowerPoint 側から読めている
- [ ] レイアウト一覧に使わないものが残っていない
- [ ] プレースホルダ文字 (「マスター タイトルの書式設定」等) が残っていない

## 8. 運用

| やりたいこと | 手順 |
|---|---|
| 新しい資料を作る | このファイルを複製して中身を消す。または既存資料で［デザイン］▸［バリエーション］▸［配色］からこの配色を選ぶ |
| 案件の色に合わせる | ［配色］▸［色のカスタマイズ］で accent1 だけ差し替える。帯・罫・表・グラフが一斉に追従する |
| テンプレートとして配る | ［名前を付けて保存］▸ PowerPoint テンプレート (.potx)。共有ドライブの 1 か所に置く |
| 色と書体だけ配る | ［配色］▸［現在の配色を保存］で .thmx |
| 書体ごと配る | ［ファイル］▸［オプション］▸［保存］▸［ファイルにフォントを埋め込む］ |
| 規約そのものを変える | このファイルを直す。資料ごとに例外を作らない |

変えてよいのは accent1 と、表紙・フッターの文字列だけ。
帯の高さ、罫の位置、文字サイズ階層を資料ごとに変えた時点で、そのファイルは標準の外に出る。

## 9. 新規作成時の進め方

1. 4.1 の必須 4 項目を聞く。既存資料があれば 4.4 で測る (聞くより正確)。
2. `scripts/tokens.py` の `TOKENS` を書き換える。色・書体・名前のみ。
3. 生成して PowerPoint でレンダリングし、7 節のチェックを通す。
4. 最小構成の 9 枚を見せて方向を確認してから、残り 7 枚を足す。
5. `.potx` を派生させ、置き場所を決める。

座標・文字サイズ階層・構図の型は既定のまま使う。
これらは `references/design-theory.md` の実測に基づいており、
相手の好みを聞いて変えるものではない。変える必要が出たら、まず理論のほうを疑う。
